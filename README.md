# Digital Cards — электронные визитки

Этап 5: личный кабинет поддерживает создание и редактирование собственных черновиков.
Логин — email. Предпросмотр и публикация будут следующим этапом.

## Запуск на этом компьютере

PostgreSQL уже подготовлена локально для проекта. Docker, pgAdmin и установка службы Windows не нужны.
Откройте PowerShell в папке `C:\Users\Пользователь\Desktop\digital-cards`:

```powershell
.\start-local.ps1
```

Скрипт запускает PostgreSQL, собирает backend и запускает API и два отдельных Angular-приложения.
Личный кабинет: http://127.0.0.1:4201 .
Публичная визитка: http://127.0.0.1:4200/stecevich-valeriy .
Ctrl+C в этом терминале останавливает все три приложения. База остаётся запущенной; её можно остановить отдельно:

```powershell
.\stop-db.ps1
```

Данные сохраняются после остановки приложений, базы и перезагрузки компьютера.
После изменения backend остановите приложения через Ctrl+C и запустите снова. Angular обновляется автоматически.
Для нового компьютера с Windows x64 и Node.js 24 сначала выполните `.\setup-local.ps1`.
Он скачает ZIP PostgreSQL 17.11 с сайта EDB, установит npm-зависимости, создаст локальную базу и примеры.
Повторная подготовка не перезаписывает существующие визитки. Перед ней обязательно остановите приложения.

## Структура

```text
digital-cards/
  public-web/    Angular: публичная страница, стили, vCard, изображения
  admin-web/     Angular: регистрация, вход, список визиток и создание черновика
  backend/       NestJS: API, SQL-схема, первоначальные данные, тесты
  scripts/       подготовка локальной базы и совместный запуск приложений
  .local/        PostgreSQL, данные, пароли и журналы — не добавлять в Git
```

- `public-web/src/app/card-page.component.ts` получает данные через HttpClient, показывает загрузку, 404 или ошибку сервера.
- `public-web/src/app/card-page.component.html` и `.css` отвечают за согласованный дизайн.
- `public-web/src/app/card.model.ts` описывает публичный ответ; `vcard.ts` формирует скачиваемый контакт.
- `public-web/proxy.conf.json` направляет `/api` на NestJS во время разработки.
- `backend/src/cards.controller.ts` принимает GET; `cards.service.ts` выбирает опубликованный снимок.
- `backend/src/public-card.ts` удаляет скрытые значения на сервере.
- `backend/database/001-cards.sql` создаёт таблицу визиток и представление только для публичного чтения.
- `backend/database/demo-card.json` заполняет базу при первой подготовке. Изменение этого файла не редактирует существующие записи.
- `npm-local.ps1` запускает npm под Node 24 для выбранного приложения. На этом компьютере использует доступный runtime Codex, не меняя системную версию Node.
- `setup-local.ps1`, `start-db.ps1`, `stop-db.ps1` управляют локальным экземпляром PostgreSQL.

Подробное объяснение backend находится в `backend/README.md`.

## Проверка результата

1. Откройте `/stecevich-valeriy`: внешний вид прежний, данные загружаются из базы.
2. Откройте http://127.0.0.1:3000/api/public/cards/stecevich-valeriy : это JSON опубликованной визитки.
3. Откройте `/draft-example` или `/unknown-card`: «Визитка не найдена». API возвращает HTTP 404.
4. В опубликованном примере имя «Стецевич Валерий», хотя в БД в его черновике другое имя.
5. Проверьте скачивание `.vcf`, кириллицу и импорт на своём телефоне.
6. Остановите приложения и базу, затем запустите заново: опубликованная визитка остаётся.
7. При работающих приложениях остановите базу и обновите страницу: появится ошибка загрузки, а не ложное сообщение об отсутствии визитки. Запустите `.\start-db.ps1` и нажмите «Попробовать снова».

Телефоны и email тестовые. Мессенджеры пока открывают сайты сервисов; персональных ссылок сотрудника нет.
Карта — внешний виджет Яндекса, ему нужен интернет. SVG eXpress условный, не официальный логотип.

## Установка, сборка и тесты

Перед переустановкой остановите приложения через Ctrl+C, чтобы Windows не блокировала esbuild.exe.
Команды выполняются из корня:

```powershell
.\npm-local.ps1 -Project public-web ci
.\npm-local.ps1 -Project backend ci
.\npm-local.ps1 -Project public-web run build
.\npm-local.ps1 -Project public-web test
.\npm-local.ps1 -Project backend run build
.\npm-local.ps1 -Project backend test
```

Backend-тестам нужна запущенная и подготовленная локальная база; frontend-тесты от неё не зависят.
Обычный `npm ci` из корня больше не применяется: каждое приложение имеет свой package.json и lock-файл.

## Локальная база

PostgreSQL слушает только `127.0.0.1:54329`. Имя базы — `digital_cards`.
Для совместимости PostgreSQL с кириллицей в Windows-пути скрипты используют системное короткое имя той же папки. Данные остаются внутри проекта на рабочем столе.
`.local/pgdata` содержит постоянные данные: не удаляйте эту папку для «очистки кэша».
Пароли создаются случайно; `.local/db-config.json` и `backend/.env` исключены из Git.
Владелец используется для подготовки и тестов. Публичные запросы используют роль `cards_public` с правами только на чтение опубликованных снимков.
Авторизация использует отдельную роль `cards_auth`: чтение/создание пользователей и управление сессиями, без доступа к таблице визиток.
Это окружение разработки, без системной службы и автоматического запуска после входа в Windows.
Для файловой резервной копии сначала остановите приложения и PostgreSQL, затем скопируйте всю `.local` в защищённое место.

## Проверка личного кабинета

На этом компьютере таблицы авторизации и зависимости кабинета уже подготовлены.
Остановите прежний запуск через Ctrl+C и выполните `./start-local.ps1`.

1. Откройте http://127.0.0.1:4201 и выберите «Регистрация».
2. Укажите email и пароль длиной 8–128 символов. После регистрации вход выполняется автоматически.
3. Обновите страницу: вход должен сохраниться.
4. Нажмите «Выйти» и войдите повторно с теми же данными.
5. Проверьте неверный пароль: кабинет не должен открыться.
6. В отдельном приватном окне http://127.0.0.1:4201/api/admin/auth/me возвращает 401.

Email пока служит логином: письма с подтверждением и восстановление пароля ещё не реализованы.
После входа отображается список собственных визиток и кнопка «Создать визитку».
Доступно создание и редактирование черновика. Публикации пока нет.

Если обновляете другую локальную копию проекта, после остановки приложений выполните:

```powershell
.\npm-local.ps1 -Project admin-web ci
.\start-db.ps1
.\npm-local.ps1 -Project backend run db:setup
.\start-local.ps1
```

Для проверки сборки кабинета: `.\npm-local.ps1 -Project admin-web run build`.

## Как устроена авторизация

- `backend/src/auth/auth.controller.ts` — маршруты register, login, me, logout.
- `auth.service.ts` — проверка данных, запросы пользователей и сессий к PostgreSQL.
- `password.ts` — асинхронный scrypt со случайной солью; исходный пароль не сохраняется.
- `session-cookie.ts` — чтение и установка HttpOnly-cookie. Срок сессии — 7 дней.
- `session.guard.ts` — серверная проверка сессии перед выдачей данных кабинета.
- `auth-request.guard.ts` — проверка Origin, JSON и ограничение частоты входа/регистрации.
- `backend/database/002-auth.sql` — таблицы users/sessions и права роли cards_auth.
- `admin-web/src/app/auth.service.ts` — HTTP-запросы кабинета.
- `admin-web/src/app/app.component.ts` — состояние страницы и обработка формы.

В таблице sessions хранится SHA-256 хеш случайного токена, а не сам токен.
Cookie не доступна JavaScript; localStorage не используется. Выход удаляет сессию из БД.
`GET /api/admin/auth/me` возвращает только id и email текущего пользователя.
POST-запросам нужен точный Origin из ADMIN_ORIGIN и Content-Type: application/json.

## Размещение без Docker

Приложение запускается непосредственно через Node.js 24, PostgreSQL работает отдельным процессом/службой.
Angular собирается в статические файлы. Docker не используется и не требуется.
Конкретную настройку службы Windows/Linux и веб-сервера выполним на этапе развёртывания.

Для production нужны `NODE_ENV=production`, `ADMIN_ORIGIN=https://<домен кабинета>`,
`DATABASE_URL` (публичная роль) и `AUTH_DATABASE_URL` (роль авторизации), `EDITOR_DATABASE_URL` (роль работы с черновиками)
и `PUBLIC_CARD_ORIGIN=https://<домен публичных визиток>`.
Пример без паролей — `backend/.env.example`. Реальные секреты не добавляйте в Git.
На домене кабинета веб-сервер должен проксировать `/api/admin` к NestJS по тому же origin.
На публичном домене достаточно проксировать `/api/public`; cookie кабинета не распространяется на соседние поддомены.
В production cookie получает Secure и требует HTTPS.

Ограничение входа: 20 запросов за 15 минут на сетевой адрес, пока в памяти одного процесса.
При работе за reverse proxy все запросы могут иметь адрес прокси: перед публикацией нужно настроить
доверенные прокси и ограничение запросов на веб-сервере. Произвольный X-Forwarded-For приложение не принимает на веру.
Перезапуск сбрасывает счётчик попыток, но не пользовательские сессии в PostgreSQL.


## Создание собственной визитки

На этом компьютере миграция уже применена. Для другой копии выполните:

```powershell
.\start-db.ps1
.\npm-local.ps1 -Project backend run db:setup
```

Перезапустите приложение через `./start-local.ps1`, чтобы backend прочитал новые настройки.

1. Войдите на http://127.0.0.1:4201 .
2. Нажмите «Создать визитку» и заполните фамилию и имя.
3. При желании добавьте отчество, должность и организацию. ФИО составится автоматически.
4. Адрес создаётся сервером автоматически. Его не нужно вводить; при редактировании он не меняется.
5. Нажмите «Сохранить черновик». Он появится в списке со статусом и датой изменения.
6. Обновите страницу: запись сохраняется в PostgreSQL.
7. Войдите другим аккаунтом в отдельном приватном окне: первой визитки там не будет.
8. Публичный URL черновика пока возвращает 404. Публикацию добавим отдельным этапом.

Демонстрационная визитка остаётся без владельца и не показывается в личных списках.
Владельца новых записей backend берёт только из сессии. Поля owner_user_id, status,
published_snapshot и любые неизвестные поля в запросе создания отклоняются.

Новые файлы:

- `backend/database/003-card-owners.sql` — колонка owner_user_id и права роли cards_editor.
- `backend/src/admin-cards/admin-cards.controller.ts` — защищённые GET/POST `/api/admin/cards`.
- `admin-cards.service.ts` — SQL с фильтром владельца, создание черновика и краткий ответ для списка.
- `create-card.input.ts` — проверка разрешённых полей и начальное содержимое черновика.
- `admin-web/src/app/cards/cards.service.ts` — HTTP-запросы списка и создания.
- `cards.component.ts`, `.html`, `.css` — состояние, форма и отображение списка.
- `backend/tests/admin-cards.test.cjs` — проверки изоляции пользователей, входных данных и прав БД.

Роль cards_editor может читать cards и вставлять только slug, draft и owner_user_id.
Миграция 004 разрешает UPDATE только колонок draft и updated_at.
Права DELETE, изменения адреса/владельца/статуса/опубликованного снимка не выданы.
Изоляцию пользователей в API обеспечивает условие owner_user_id из сессии в SQL;
роль БД сама по себе не различает пользователей сайта.
Публичная роль cards_public и роль авторизации cards_auth сохраняют прежние права.

Список пока загружается целиком. Постраничную загрузку добавим при необходимости.
Ограничение частоты запросов также применяется к созданию черновиков: 20 запросов за 15 минут
на сетевой адрес суммарно с регистрацией и входом в рамках одного процесса.


## Редактирование черновика

Сборку и запуск выполняет пользователь. После обновления кода остановите прежний запуск через Ctrl+C.
При переносе изменений в другую копию проекта сначала примените миграцию, затем запустите приложение:

```powershell
.\npm-local.ps1 -Project backend run db:setup
.\start-local.ps1
```

1. В списке визиток нажмите «Редактировать».
2. Измените ФИО, должность, организацию или контакты. Доступны Telegram, WhatsApp, MAX и eXpress.
3. Изображения пока задаются HTTP/HTTPS ссылками или путями /assets/…; загрузки с компьютера ещё нет.
4. У каждого необязательного поля есть переключатель «Показывать на визитке».
5. В разделе «Блоки визитки» можно скрыть целую группу. Значения остаются в личном черновике.
6. Нажмите «Сохранить изменения», затем откройте редактор ещё раз — данные должны сохраниться.
7. ФИО формируется из фамилии, имени и отчества. Отдельного поля для него больше нет.
8. Адрес формируется автоматически при создании. Старые адреса сохраняются, включая введённые вручную ранее.

Редактирование не меняет опубликованный снимок. Постоянный адрес, владелец и статус также остаются прежними.
PUT сохраняет весь набор редактируемых полей черновика, поэтому клиент отправляет полную форму.
Если редактировать один черновик в двух вкладках одновременно, сохраняется последняя отправленная версия.

Новые файлы редактора:

- `backend/src/admin-cards/card-draft.input.ts` — проверка типов, длины текста, ссылок, переключателей и списка разрешённых полей.
- `backend/database/004-edit-drafts.sql` — право записи только в draft и updated_at.
- `admin-web/src/app/cards/card-draft.model.ts` — структура редактируемых данных.
- `card-editor.component.ts`, `.html`, `.css` — отдельная форма редактора; список остаётся в cards.component.
- `backend/tests/edit-drafts.test.cjs` — проверки доступа владельца, неизменности URL и опубликованного снимка, валидации ссылок.

Существующий `public-card.ts` не изменён: при публичной выдаче он по-прежнему удаляет выключенные значения.
Поле displayName остаётся в публичном API для совместимости, но вычисляется сервером, а не вводится пользователем.

Для ручного запуска автоматических проверок после сборки:

```powershell
.\npm-local.ps1 -Project backend run build
.\npm-local.ps1 -Project backend test
.\npm-local.ps1 -Project admin-web run build
```
